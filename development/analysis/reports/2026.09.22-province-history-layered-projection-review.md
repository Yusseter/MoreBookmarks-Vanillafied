treating every repeated province ID as a runtime conflict. Tiger's
[province-history loader](https://github.com/amtep/tiger/blob/main/src/ck3/data/prov_history.rs)
explicitly accepts multiple entries and appends the later block to the existing
province data.

## Evidence

- All seven current block pairs exactly match the pre-merge Yusseter baseline.
- Every pair contains the complete current upstream block multiset plus one
  additional preexisting Yusseter block.
- Every pair includes a block explicitly marked with a `Yusseter: MPE` donor
  comment.
- No pair contains a conflicting direct field value.
- `5276`, `5279`, `5280`, `5281`, and `5321` have disjoint additive fields and
  dated entries.
- `606` and `5344` repeat only identical values. The repeated keys are
  `holding` for both provinces and `1320.1.1` additionally for `606`.

The two identical overlaps are optional cleanup, not correctness fixes.
Consolidating these blocks would mix the source-owned history and the MPE
projection layer, increasing future upstream merge risk without changing the
effective values.

## Classification

All seven rows are classified as
`intentional_additive_mpe_province_projection`, priority `P3`, with action
`retain_layered_mpe_province_history_projection`.

The rule is evidence-based rather than ID-specific. It requires all of the
following:

- current blocks still match the pre-merge baseline;
- the current block multiset contains every current upstream block;
- at least one additional current block remains;
- an explicit MPE donor block is present;
- no direct field conflict exists.
